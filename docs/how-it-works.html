Realtime Fintech Dashboard

Что сделано и как это работает

Учебное приложение: живая таблица выдуманных инструментов и страница настроек генератора. Биржа и матчинг ордеров не моделируются. Случайный шаг цены считает Rust, собранный в WebAssembly и запущенный внутри Web Worker. Метрики считает TypeScript в том же воркере.

Что входит в проект

Стек зафиксирован так: Angular 22, standalone-компоненты, strict TypeScript, маршруты /dashboard и /settings. Старт с дашборда. Генератор — крейт wasm/market-producer на Rust, сборка wasm-pack --target web. Тесты генератора — cargo test. Тесты приложения — ng test на Vitest, без e2e и без ожидания настоящего таймера.

Настроек в браузере после перезагрузки нет. Деплоя, GitHub Actions, бенчмарка и настоящей биржи тоже нет. История событий не хранится: на инструмент остаются только текущие суммы и последний снимок стакана.

Цены внутри — целые центы. 10200 означает $102.00. Объём и числитель VWAP копятся в bigint, чтобы сумма не потеряла младшие центы после 2^53. Деление и округление до центов на экране делает только src/app/format/format-metric.ts. Стратегии отдают сырые суммы.

Два экрана

Оболочка src/app/app.ts рисует ссылки Dashboard и Settings. Сам продюсер она не создаёт. Его один раз поднимает provideAppInitializer в src/app/app.config.ts: так подписка страницы не может породить второй Worker. Экран обновляется без Zone.js, через provideZonelessChangeDetection().

Дашборд

Одна строка на инструмент: ALFA, BETA и дальше по списку фабрики. Колонки Last, Spread, Volume, VWAP, Imbalance. Кнопка Pause/Resume и короткая русская строка статуса: «Запуск генератора…», «Генерация идёт», «Пауза», «Ошибка инициализации», «Ошибка генерации». Первая ошибка — если Worker или Wasm не поднялись, вторая — если генерация оборвалась уже после started. Если запуск не удался, под статусом виден role="alert" с текстом ошибки, а не пустая страница. До первых данных цены и дисбаланс показываются как «н/д», объём равен 0.

Настройки

Три целых поля. Правка инпута ничего не меняет, пока не нажата Apply. На странице отдельно написано, какие значения уже применены. Ошибки всех полей показываются списком.

Поле По умолчанию Диапазон
instrument count 5 1–50
updates per batch 100 1–1000
batch interval ms 500 50–2000

100 событий за 500 мс — это 200 событий в секунду на все инструменты вместе, не на каждый. Один инструмент может встретиться в пачке несколько раз.

Как событие доходит до таблицы

Главный поток не видит сырой поток. Даже на верхней скорости (1000 событий каждые 50 мс) интерфейс получает уже свёрнутый снимок, и не чаще одного кадра. Каждая сделка к этому моменту уже лежит в суммах.

1. Страница Кнопка вызывает ProducerFacade.pause(), resume() или apply(). Шаблон подписан на snapshot$ и status$ через async pipe.
2. Команда Фасад создаёт одну из трёх команд и вызывает execute. Другого пути у кнопки и у unit-теста нет.
3. Автомат и фабрика Команда спрашивает SessionMachine, можно ли перейти. Apply после проверки чисел вызывает SessionFactory.create: новый runId, имена, seed, размер пачки и интервал.
4. WorkerClient Единственный Worker получает start, pause или resume. В каждом сообщении есть runId.
5. Воркер и Wasm MarketGenerator.fillBatch пишет пачку в линейную память. Адаптер копирует семь i32 в список MarketUpdate. Книга инструментов сразу обновляет пять стратегий.
6. Кадр SnapshotGate помечает снимок грязным на каждое событие, а postMessage делает не чаще одного requestAnimationFrame.
7. Прокси RunGuard сравнивает runId с текущей сессией. Чужое сообщение выбрасывается целиком, до чтения строк и текста ошибки.

Страницы не знают про Worker, Wasm, runId и память модуля. Это граница фасада в src/app/producer/facade/producer-facade.ts.

Пять метрик

Общий интерфейс стратегии — update(event) и read(). Цикл в InstrumentAccumulator только вызывает их. Формулы живут в отдельных классах. У каждого имени свой аккумулятор, поэтому две акции с одинаковыми сделками не делят суммы.

Метрика Откуда Формула
Last последняя сделка priceCents. До первой сделки значение недоступно.
Spread последний снимок стакана askCents − bidCents. Старые снимки не усредняются.
Volume сумма с начала запуска только tradeQuantity. Количества стакана в объём не входят. До сделок объём 0 и это нормальное значение.
VWAP те же суммы, без окна по времени sum(priceCents × tradeQuantity) / sum(tradeQuantity). Нулевой знаменатель — недоступно, не NaN.
Imbalance последний снимок стакана (bidQuantity − askQuantity) / (bidQuantity + askQuantity), от −1 до +1. Нулевой знаменатель и отсутствие снимка — недоступно.

Пример из задания

Две сделки одного инструмента: 10 штук по $100 и 30 штук по $102. У второй сделки bid $101.96, ask $102, bid qty 600, ask qty 400. Спред и дисбаланс берутся только из неё. 

last     = 10200 центов            = $102.00
volume   = 10 + 30                  = 40
notional = 10000×10 + 10200×30      = 406000
VWAP     = 406000 / 40              = 10150 центов = $101.50
spread   = 10200 − 10196            = 4 цента      = $0.04
imbalance = (600 − 400) / (600 + 400) = 0.20

Этот расчёт лежит в src/app/metrics/metrics.spec.ts и идёт через книгу инструментов, а не через отдельный калькулятор в тесте. На экране доля 0.20 становится +0.20, отрицательный ноль после округления — 0.00, а объём получает разделители тысяч. Округление по-прежнему только в formatMetric.

Жизненный цикл сессии

Фазы и переходы записаны таблицей в src/app/producer/state/session-machine.ts. Если перехода нет, transition возвращает false и фазу не меняет. Команда в этом случае не зовёт воркер, снимок остаётся прежним.

Откуда Событие Куда
idle apply starting
starting ready / fail / apply running / failed / starting
running pause / fail / apply paused / failed / starting
paused resume / fail / apply running / failed / starting
failed apply starting

Старт приложения

Конструктор фасада сразу выполняет Apply с настройками по умолчанию. Машина идёт idle → starting. Воркер отвечает started, машина переходит в running. Пока ответа нет, на экране «Запуск генератора…» и пустые строки: цены «н/д», объём 0.

Pause и Resume

Pause разрешён только из running. Воркер снимает один setTimeout и перестаёт просить пачки. Суммы и таблица не обнуляются. Resume ставит ровно один следующий тик через текущий интервал. Пропущенные за паузу пачки не догоняются: насос в src/app/worker/batch-pump.ts не копит очередь. Повторный Pause в паузе и Resume на ходу отбрасываются.

Apply

Apply можно нажать из любой фазы, в том числе из паузы и из ошибки. Порядок такой:

  1. Цепочка валидации собирает ошибки всех полей. Если список не пуст, сессия не меняется.
  2. Машина переходит в starting. Если переход вдруг недопустим, фабрика не вызывается.
  3. SessionFactory.create выдаёт новый runId, seed и имена. Это единственное место, где сессия рождается. Страницы фабрику не вызывают.
  4. На экран сразу кладётся пустой снимок новых имён, чтобы старые итоги не висели до первой пачки.
  5. Воркер получает start. Он останавливает насос, вызывает free() у старого генератора и только потом создаёт новый MarketGenerator и новую книгу сумм.
Apply во время паузы и сбрасывает суммы, и снова запускает генерацию. Это не Resume: старые итоги не продолжаются.

Чужой runId

После Apply из воркера ещё может приехать снимок или ошибка прошлого запуска. У каждого сообщения есть runId. RunGuard.accept возвращает null, если id не совпал с текущей сессией, и фасад на этом выходит. Ни одна цифра и ни текст ошибки старого запуска не записываются. Тот же приём внутри воркера: если за время загрузки Wasm успел прийти более новый start, старое продолжение генератор не создаёт.

При уничтожении фасада WorkerClient.terminate() вызывает worker.terminate() один раз. Повторный destroy второй раз воркер не трогает.

Генератор на Rust

Wasm делает только шаг рынка. Готовых метрик он не считает. Состояние цены каждого инструмента хранится внутри модуля между вызовами. Имена приходят снаружи: фабрика сессии строит список ALFA, BETA, … и передаёт его в конструктор. Число инструментов генератор из воздуха не берёт. Пустой список имён отвергается.

Случайность — xorshift32 с seed. Seed 0 заменяется на 1, потому что нулевое состояние генератора больше не меняется. Тесты зовут next_batch с фиксированным seed и проверяют инварианты без таймеров.

Один шаг для одного события:

  1. Выбирается индекс инструмента из переданного списка.
  2. Новая цена bid получается из предыдущей. К ней прибавляется слабый возврат к якорю $100.00 — четверть процента разрыва за шаг — и шум от −15 до +15 базисных пунктов текущей цены, но не меньше 1 цента, если шум ненулевой. Ниже 1 цента цена не опускается. Стартовая цена каждого инструмента — 10000 центов, то есть $100.00.
  3. Спред — случайные 1–40 базисных пунктов цены bid, но не меньше 1 цента. Ask строго больше bid. Если сумма не помещается в i32, bid опускается так, чтобы ask ещё поместился.
  4. Цена сделки этого события равна его bid или его ask, не середине.
  5. Объём сделки — от 1 до 100. Количества стакана помнят предыдущее значение, тянутся к 400 и гуляют на ±25, оставаясь в диапазоне 0–2000. В торговый объём они не входят.

fill_batch(count) пишет ровно count событий в Vec<i32> и возвращает указатель. Указатель жив до следующего вызова. Семь полей одной записи, в этом порядке: 

0 instrument index
1 trade price, cents
2 trade quantity
3 bid cents
4 ask cents
5 bid quantity
6 ask quantity

Адаптер src/app/wasm/wasm-adapter.ts читает Int32Array из WebAssembly.Memory и сразу копирует числа в обычные объекты MarketUpdate. Метрики буфер не видят. Индекс — это позиция в том же массиве имён, который фабрика передала генератору.

Воркер

Файл src/app/worker/market.worker.ts грузит /market-wasm/market_producer_bg.wasm один раз и переиспользует модуль. На каждый start создаётся новый генератор. Пачки просит BatchPump: после обработки одной пачки ставится один setTimeout на интервал сессии. Это не setInterval, поэтому опоздавший тик не складывается с новым.

Снимок наружу отдаёт SnapshotGate. Два обновления до кадра дают одну публикацию, и в ней уже обе сделки. Если кадр сброшен вместе со сменой сессии, старые суммы не уходят. В обычном воркере кадр — это requestAnimationFrame. Если его нет, запасной путь — один setTimeout на 16 мс, то есть всё равно не чаще кадра.

Ошибка загрузки Wasm уходит на страницу текстом «Не удалось инициализировать генератор Wasm: …» и стадией startup. Ошибка уже идущей пачки — «Генератор остановился: …» и стадией runtime. После такой ошибки объект генератора отпускается: следующий fillBatch на нём не зовётся. Оба сообщения переводят сессию в failed, если runId ещё текущий. Если конструктор Worker бросает исключение, клиент сообщает об этом из start(), уже после подписки фасада, и следующий start() пробует поднять воркер снова. Если скрипт воркера не загрузился или воркер умер с необработанной ошибкой, объект завершается, и следующий Apply получает новый Worker, а не сообщение в пустоту.

Как проверяются настройки

Поле формы — строка. parseDraftNumber пропускает дальше только десятичные цифры. «5.5», «0x10», «1e3» и пустая строка числом не становятся: дробь не обрезается, а hex и экспонента не читаются как целые. Дальше у каждого поля своя цепочка из двух звеньев: сначала «это целое число» (пустое поле — «Поле обязательно.»), потом «оно внутри min/max». Третьего звена нет. Если значение не целое, диапазон для этого поля уже не спрашивается. Три поля проверяются все, даже когда первое уже плохое. ApplySettingsCommand вызывает один раз parseSettings.

Сообщения на русском, с именем поля: «Число инструментов: Допустимый диапазон 1–50.», «Событий в пачке: Ожидается целое число.». Apply с таким списком фабрику не вызывает.

Десять паттернов и зачем они здесь

Полная защита каждого решения, включая отказ от соседнего паттерна, лежит в docs/design-patterns.md. Коротко по коду:

Паттерн Где Какую дыру закрывает
Одиночка ProducerFacade, providedIn: 'root' Один воркер на приложение. Класса с getInstance() нет: экземпляр даёт DI.
Состояние SessionMachine Pause, Resume и Apply — переходы таблицы, а не россыпь флагов.
Фабричный метод SessionFactory.create Сессию рождает только Apply. Новый runId и чистые суммы, без клонирования старых.
Фасад ProducerFacade Странице доступны снимок, статус, три действия и применённые настройки.
Команда Pause, Resume, ApplySettings Кнопка и тест выполняют один execute. Четвёртой команды нет.
Заместитель RunGuard Чужой runId выбрасывается целиком.
Адаптер readMarketUpdates Плоские i32 становятся MarketUpdate. Метрик адаптер не считает.
Стратегия пять классов в src/app/metrics Формула отделена от цикла пачки. Недоступность — явный результат.
Наблюдатель RxJS snapshot$ и status$ Своего списка слушателей нет. Подписка страницы — async pipe.
Цепочка обязанностей IntegerLink → RangeLink Два звена на поле. Форма показывает ошибки всех полей сразу.

Сознательно не используются Builder, Prototype, Abstract Factory, Bridge, Composite, Decorator, Flyweight, Iterator, Mediator, Memento, Template Method и Visitor. Коротко: Builder не нужен для трёх чисел, Memento противоречит запрету хранить историю, Mediator повторил бы фасад, а формат валюты — функция показа, не декоратор.

Что покрыто тестами

  • Пример из ТЗ, нулевой знаменатель VWAP и дисбаланса, объём без количеств стакана, две акции не смешивают суммы.
  • Цепочка настроек: целое раньше диапазона, границы 1/50, 1/1000, 50/2000, все ошибки сразу, дробь не обрезается.
  • Невалидный Apply не вызывает фабрику и не шлёт новый start.
  • Apply сбрасывает снимок. Сообщение со старым runId не меняет цифры и не затирает статус. Ошибка нового запуска на экран попадает.
  • Pause оставляет снимок, повторный Pause воркер не зовёт. Resume не очищает таблицу. Apply из паузы шлёт новый start, а не только resume.
  • Насос пачек: тик после Pause ничего не производит, Resume ставит один следующий тик. Снимок публикуется один раз на кадр, уже с полной суммой.
  • Адаптер читает раскладку из семи i32 и копирует числа из памяти модуля.
  • worker.terminate() вызывается один раз.
  • Rust: длина пачки, bid < ask, цена сделки равна bid или ask, шаг цены не больше 15 центов от предыдущей, seed повторяем, состояние живёт между вызовами, индекс не выходит за переданный список имён.

Таймеры в тестах подменены: колбэк вызывается руками. Реальных 500 мс тесты не ждут.

Как собрать и проверить

Нужны Node.js 22+, Rust stable и wasm-pack. На macOS:

brew install wasm-pack
rustup target add wasm32-unknown-unknown
npm install
npm start

npm start сначала выполняет wasm-pack build wasm/market-producer --target web --release и кладёт клей в public/market-wasm. Этот каталог в git не входит. Затем поднимается приложение на http://localhost:4200. 

npm test
npm run test:generator

Первая команда — ng test --watch=false. Вторая — cargo test --manifest-path wasm/market-producer/Cargo.toml.
