# Паттерны

Источник смысла: [Паттерны проектирования](https://refactoring.guru/ru/design-patterns).

Ниже ровно десять паттернов, которые есть в коде. Каждый закрывает пункт ТЗ. Там, где механизм уже есть в Angular или RxJS, своего списка слушателей и `getInstance()` нет.

## 1. Одиночка (Singleton)

**Пункт ТЗ.** Один Worker на всё приложение. Переход между `/dashboard` и `/settings` сохраняет запуск и режим run/pause и не создаёт второй продюсер. Подписка страницы не должна поднимать воркер заново. При уничтожении сервиса `worker.terminate()` вызывается один раз.

**Проблема.** Маршрутизатор создаёт и уничтожает компоненты страниц. Если продюсер живёт в компоненте, уход на настройки и возврат откроют второй Worker, а старые суммы останутся в первом.

**Почему этот паттерн.** Нужен один экземпляр на время жизни приложения, общий для обеих страниц.

**Почему не соседний.** Класс с `getInstance()` не пишется: одиночку даёт DI. `providedIn: 'root'` создаёт `ProducerFacade` один раз и вызывает `ngOnDestroy`, когда приложение уничтожается. Статический синглтон спрятал бы это время жизни и не дал бы тесту подставить фальшивый `WorkerClient`. Глобальная `let` в модуле тоже была бы одним экземпляром, но без хука уничтожения.

**Файлы.**

- `src/app/producer/facade/producer-facade.ts` — `@Injectable({ providedIn: 'root' })`
- `src/app/app.config.ts` — инициализатор создаёт фасад при старте приложения, а не при подписке страницы; там же один `WorkerClient`

## 2. Состояние (State)

**Пункт ТЗ.** Жизненный цикл сессии: idle/starting, running, paused, failed. Pause из running переводит в paused и перестаёт запрашивать пачки. Resume возвращает в running и не создаёт сделки за время паузы. Apply из любого состояния создаёт новый запуск и переводит в running. Недопустимый переход не меняет данные.

**Проблема.** Если держать `isPaused` и `isFailed` отдельно, Pause из паузы и Resume на ходу начинают спорить, и легко обнулить таблицу «заодно».

**Почему этот паттерн.** Допустимые переходы — это таблица, а не набор условий, размазанных по кнопкам.

**Почему не стратегия.** Стратегии в этом проекте — пять формул метрик. Они не знают, можно ли сейчас нажать Pause. Конечный автомат знает только фазу. Пауза таймера живёт в `BatchPump`, но решение «переход разрешён» принимает автомат: если `transition` вернул false, воркер не вызывается и снимок не трогается.

**Файлы.**

- `src/app/producer/state/session-machine.ts`
- `src/app/worker/batch-pump.ts` — после разрешённого перехода снимает один таймер и не копит пропущенные пачки

## 3. Фабричный метод (Factory Method)

**Пункт ТЗ.** Apply — единственное место рождения сессии: новый `runId`, набор имён инструментов, экземпляр генератора, чистые суммы. Старая сессия до этого останавливается и освобождается. Страницы сессию не конструируют. Имена строит TypeScript и передаёт их в генератор; генератор сам число инструментов не выдумывает.

**Проблема.** Если дашборд или форма сами соберут `runId` и список имён, при навигации появится второй запуск, а старые суммы можно случайно скопировать в новый.

**Почему этот паттерн.** Создание собрано в один метод `SessionFactory.create`. Его вызывает только `ApplySettingsCommand`, и только после успешной валидации и разрешённого перехода `apply`.

**Почему не абстрактная фабрика.** Продукт один — запись сессии. Семейств «бумажный генератор / боевой генератор» нет, параллельная иерархия продуктов была бы пустой. Иерархии создателей тоже нет: подкласс фабрики не нужен, чтобы выдать следующий `runId`.

Чистые суммы и объект `MarketGenerator` появляются в воркере из этой записи, потому что и Wasm, и аккумуляторы обязаны жить в воркере. `start` сначала останавливает насос и вызывает `free()` у старого генератора, потом создаёт новый. На главный поток сразу уходит пустой снимок, чтобы старые итоги не висели до первой пачки.

**Файлы.**

- `src/app/producer/session-factory/session-factory.ts`
- `src/app/producer/commands/commands.ts` — единственный вызов `create`
- `src/app/worker/market.worker.ts` — освобождение старого генератора и новый экземпляр с переданным списком имён
- `src/app/metrics/instrument-book.ts` — новый экземпляр книги и есть нулевые суммы

## 4. Фасад (Facade)

**Пункт ТЗ.** Компонентам доступен один сервис: `snapshot$`, `status$`, `pause()`, `resume()`, `apply(settings)` и текущие применённые настройки. Компонент не знает про Worker, Wasm, `runId` и память модуля.

**Проблема.** У страницы иначе был бы выбор из десятка внутренних типов. Любая из них могла бы прочитать чужой `runId` или забыть освободить воркер.

**Почему этот паттерн.** Фасад прячет сессию, автомат, фабрику, прокси и воркер за одним API.

**Почему не посредник.** Страницы не общаются друг с другом. Им не нужен объект, который рассылает сообщения между дашбордом и формой. Обе просто вызывают один и тот же фасад. Посредник продублировал бы его.

**Файлы.**

- `src/app/producer/facade/producer-facade.ts`
- `src/app/pages/dashboard/dashboard-page.ts`
- `src/app/pages/settings/settings-page.ts`

## 5. Команда (Command)

**Пункт ТЗ.** Три команды и только три: Pause, Resume, ApplySettings. Их выполняет фасад. Кнопки и unit-тесты идут одним путём. Команд «на будущее» нет.

**Проблема.** Если кнопка сама двигает автомат, а тест вызывает другой метод, Pause из паузы можно починить в одном месте и оставить сломанным в другом.

**Почему этот паттерн.** Действие пользователя — объект с `execute`. Фасад только создаёт его и запускает. Тест команды проверяет тот же `execute`.

**Почему не стратегия.** Стратегия здесь подменяет формулу метрики. Команда — это одно из трёх действий над сессией. Общий интерфейс с одним типом возврата не вводился: Apply возвращает список ошибок валидации, Pause и Resume — удалось ли перейти. Склеивать это в одну сигнатуру «на будущее» ТЗ запрещает.

**Файлы.**

- `src/app/producer/commands/commands.ts`
- `src/app/producer/facade/producer-facade.ts` — `pause()`, `resume()`, `apply()` только создают команду
- `src/app/pages/dashboard/dashboard-page.html` — кнопка вызывает `pause` или `resume` фасада
- `src/app/pages/settings/settings-page.ts` — Apply вызывает `facade.apply`

## 6. Заместитель (Proxy), защищающий

**Пункт ТЗ.** Каждое сообщение воркера несёт `runId`. В снимок оно попадает только если id совпал с текущей сессией. Чужой `runId` отбрасывается целиком. Сообщение старого запуска не имеет права затереть новый. Событие со старым `runId` после Apply не меняет ни одну цифру.

**Проблема.** Apply уже сбросил суммы, а из воркера ещё может приехать снимок или ошибка предыдущего запуска. Если прочитать из него хотя бы объём, новый экран будет врать.

**Почему этот паттерн.** Прокси стоит на границе и решает, пропускать сообщение или выбросить его до того, как фасад посмотрит на строки и текст ошибки.

**Почему не декоратор.** Декоратор добавляет поведение к объекту, не меняя интерфейс. Здесь нечего оборачивать: нужно отбраковать чужое сообщение целиком. Проверка в шаблоне была бы поздно — снимок уже лёг бы в `BehaviorSubject`.

**Файлы.**

- `src/app/producer/run-guard/run-guard.ts`
- `src/app/producer/facade/producer-facade.ts` — `onWorkerEvent` при `null` выходит сразу
- `src/app/worker/worker-protocol.ts` — `runId` есть у каждого сообщения
- `src/app/worker/market.worker.ts` — запоздавший `start` тоже сверяет `runId`, чтобы старая инициализация не подняла генератор поверх новой

## 7. Адаптер (Adapter)

**Пункт ТЗ.** Граница Wasm: плоские числа из линейной памяти превращаются в список доменных `MarketUpdate`. Домен и компоненты типы Wasm не видят. Адаптер не считает метрики. Wasm делает только шаг генерации.

**Проблема.** В памяти модуля лежит `i32` подряд: индекс, цена в центах, количество, bid, ask, количества стакана. Если стратегия сама читает буфер, формула VWAP оказывается привязана к смещению поля.

**Почему этот паттерн.** Адаптер — единственное место, которое знает порядок семи полей. Наружу выходит обычный объект. Числа копируются сразу, чтобы следующий вызов Wasm не переписал уже прочитанную пачку.

**Почему не фасад.** Фасад — API для страниц. Адаптер не прячет воркер и не знает про паузу. Он переводит одну запись ABI в один `MarketUpdate` и на этом заканчивается.

**Файлы.**

- `src/app/wasm/wasm-adapter.ts`
- `src/app/wasm/market-update.ts` — доменный тип, без указателей и `WebAssembly.Memory`
- `wasm/market-producer/src/lib.rs` — пишет ту же раскладку в `fill_batch`

## 8. Стратегия (Strategy)

**Пункт ТЗ.** Пять метрик с общим интерфейсом «обновить аккумулятор одним `MarketUpdate`» и «прочитать значение для экрана»: Last, Spread, Volume, VWAP, Imbalance. Общий цикл пачки их только вызывает. Формулы и тест примера живут здесь. Недоступное значение — явный результат, не `NaN`. До первых данных цены и дисбаланс недоступны, объём 0. Если знаменатель 0, значение недоступно. Спред и дисбаланс — из последнего снимка, объём и VWAP — из сумм. Объём растёт только на `tradeQuantity`. Окно VWAP по времени запрещено. Две акции не делят один аккумулятор. Полную историю не хранить.

**Проблема.** Один `switch` в цикле пачки смешает «последний снимок» и «сумма с начала запуска». Пример из ТЗ тогда негде положить отдельно от воркера.

**Почему этот паттерн.** У каждой метрики свой объект с `update` и `read`. Цикл в аккумуляторе не знает формул. У каждого инструмента свой набор из пяти стратегий, поэтому одинаковые сделки ALFA и BETA не складываются.

**Почему не шаблонный метод и не посетитель.** Шаблонный метод вынес бы общий алгоритм в базовый класс с переопределяемыми шагами. Общий алгоритм здесь — один цикл `for`. Базовый класс ради него ничего не спрячет. Посетителю нужно дерево элементов и двойная диспетчеризация. Событие одно, плоское, а меняются формулы, не структура дерева.

**Файлы.**

- `src/app/metrics/metric-strategy.ts`
- `src/app/metrics/last-price-strategy.ts`
- `src/app/metrics/spread-strategy.ts`
- `src/app/metrics/volume-strategy.ts`
- `src/app/metrics/vwap-strategy.ts`
- `src/app/metrics/imbalance-strategy.ts`
- `src/app/metrics/instrument-accumulator.ts` — общий цикл
- `src/app/metrics/instrument-book.ts` — отдельный аккумулятор на имя
- `src/app/metrics/metric-reading.ts` — явный `unavailable`
- `src/app/metrics/metrics.spec.ts` — пример из ТЗ

## 9. Наблюдатель (Observer)

**Пункт ТЗ.** Фасад отдаёт снимок и статус через RxJS `Observable`. Страницы подписываются. Свой список слушателей не писать. Переход между страницами сохраняет запуск: новая страница видит тот же поток.

**Проблема.** Если фасад хранит `Set` колбэков, каждая страница обязана не забыть отписку, а тест фасада начинает зависеть от этого списка.

**Почему этот паттерн.** Наблюдатель здесь — это RxJS. `BehaviorSubject` держит последнее значение, `asObservable()` не даёт странице вызвать `next`. В шаблоне подписка — `async` pipe, она же отписывается при уничтожении компонента.

**Почему не посредник.** Посредник координировал бы страницы между собой. Страницы не знают друг о друге. Они независимо наблюдают один фасад.

**Файлы.**

- `src/app/producer/facade/producer-facade.ts` — `snapshot$`, `status$`, `appliedSettings$`
- `src/app/pages/dashboard/dashboard-page.html`
- `src/app/pages/settings/settings-page.html`

## 10. Цепочка обязанностей (Chain of Responsibility)

**Пункт ТЗ.** Проверка одной настройки: сначала «целое число», потом «диапазон». У каждого поля своя цепочка с min/max. Форма показывает все ошибки. Apply с ошибкой сессию не меняет. Цепочка из двух звеньев на поле, без третьего звена «просто так». Значения целые: число инструментов 1–50, событий в пачке 1–1000, интервал 50–2000 мс.

**Проблема.** Одна функция с тремя `if` прячет порядок проверок. Дробь `5.5` легко молча обрезать через `parseInt` и принять как `5`, не показав ошибку.

**Почему этот паттерн.** У звена есть `setNext`. На поле собираются ровно два: `IntegerLink`, затем `RangeLink`. Первое звено, которое нашло ошибку, дальше не передаёт значение. Три поля проверяются все, даже если первое уже плохое, и форма получает весь список.

**Почему не декоратор.** Декоратор наслаивает поведение на объект. Здесь нет объекта настройки, который надо обернуть: по цепочке идёт одно значение черновика. Третье звено «формат» или «положительность» не добавляется — положительность уже сидит в диапазоне.

**Файлы.**

- `src/app/settings/settings-chain.ts`
- `src/app/settings/parse-draft.ts` — не режет дробную часть до цепочки
- `src/app/settings/generator-settings.ts` — модель трёх чисел и значения по умолчанию
- `src/app/producer/commands/commands.ts` — при непустом списке ошибок `create` не вызывается
- `src/app/pages/settings/settings-page.html` — показывает все строки ошибок

## Что сознательно не используется

**Строитель (Builder).** Настройки — три числа. Для них хватает объекта. Пошаговый строитель с директором ничего не собирает, чего не собирает литерал.

**Прототип (Prototype).** Новый запуск обязан начать с нулевых сумм. Клон живой сессии утащил бы объём и VWAP. Сессия каждый раз создаётся фабрикой, а не копируется.

**Абстрактная фабрика (Abstract Factory).** Нет семейств связанных продуктов. Генератор один, снимок один, сессия одна.

**Мост (Bridge).** Нет двух независимых иерархий «абстракция × реализация», которые надо менять отдельно. Воркер и Wasm разделены адаптером и протоколом сообщений, это граница ABI, а не мост.

**Компоновщик (Composite).** Инструменты — плоский список строк таблицы. Дерева «папка инструментов» нет, и считать метрики по узлам не нужно.

**Декоратор (Decorator).** Формат валюты — функция показа в `src/app/format/format-metric.ts`. Округлять обёрткой над стратегией значило бы спрятать правило «округление только на экране». Недоступное значение — вариант типа, а не декоратор вокруг `NaN`.

**Приспособленец (Flyweight).** Суммы инструмента уникальны и изменяемы. Общий легковес на две акции как раз смешал бы аккумуляторы, что ТЗ запрещает. Общие только неизменяемые имена из списка фабрики, и для этого отдельный паттерн не нужен.

**Итератор (Iterator).** Пачка — массив. Её обходит обычный `for`. Свой итератор не добавляет правила ТЗ.

**Посредник (Mediator).** Он повторил бы фасад. Страницы не согласуют действия друг с другом: обе говорят только с продюсером.

**Хранитель (Memento).** ТЗ запрещает хранить историю событий. Нужны текущие суммы и последний снимок. Пауза не откатывает таблицу к прошлому снимку и не восстанавливает его из снимка: цифры просто перестают расти. Снимок для отката противоречил бы этому.

**Шаблонный метод (Template Method).** Цикл пачки — прямой код в аккумуляторе: вызвать `update` у каждой стратегии. Выносить это в абстрактный базовый класс с хуками значило бы наследование ради нескольких вызовов.

**Посетитель (Visitor).** Набор метрик стабилен, но это не дерево рыночных объектов, по которому ходит внешний посетитель. Формула живёт в стратегии и тестируется напрямую. Двойная диспетчеризация здесь ничего не разделяет.
