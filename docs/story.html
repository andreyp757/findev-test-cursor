Связный разбор проекта

Как работает Realtime Fintech Dashboard

Это маленькое Angular-приложение. На экране живая таблица выдуманных инструментов и страница настроек. Рынок не настоящий: цены придумывает генератор. Генератор написан на Rust, собран в WebAssembly и работает внутри Web Worker. Метрики таблицы считает TypeScript в том же Worker. Ниже один проход по системе: кто кого вызывает, зачем каждый файл и как здесь устроен каждый паттерн.

Сначала весь путь

От кнопки до строки таблицы

В приложении два маршрута. /dashboard показывает таблицу. /settings показывает форму. Пустой адрес и неизвестный адрес ведут на /dashboard. Это записано в src/app/app.routes.ts. Коридор с двумя ссылками — App в src/app/app.ts. Он сессию не создаёт.

Сессию создаёт Фасад ProducerFacade. Angular создаёт его один раз на всё приложение. Это Одиночка, и делает её не рукописный getInstance(), а зависимость с providedIn: 'root'. Создаёт фасад не страница, а provideAppInitializer в src/app/app.config.ts. Поэтому переход между Dashboard и Settings не поднимает второй Web Worker.

Фасад сразу выполняет команду Apply с настройками по умолчанию: 5 инструментов, 100 событий в пачке, пауза между пачками 500 миллисекунд. Команд ровно три. Это паттерн Команда: PauseCommand, ResumeCommand, ApplySettingsCommand. Кнопка и unit-тест вызывают тот же execute, что и фасад.

Перед делом команда спрашивает Состояние SessionMachine. У сессии фазы idle, starting, running, paused, failed. Переход, которого нет в таблице, возвращает false и данные не меняет. Apply разрешён из любой фазы. Pause разрешён только из running. Resume только из paused.

Если Apply прошёл проверку чисел, Фабричный метод SessionFactory.create рождает сессию. Больше никто её не рождает. В сессии новый runId, список имён инструментов, seed и параметры пачки. Имена начинаются с ALFA, BETA. Генератор сам количество инструментов не выдумывает: ему передают этот список. Суммы в фабрике не копируются. Новый запуск начинает с нуля.

Фасад сразу публикует пустой снимок, чтобы старые итоги не висели на экране, и просит WorkerClient отправить Worker сообщение start. В сообщении есть runId. WorkerClient держит один Worker. При уничтожении фасада он вызывает worker.terminate() один раз.

Worker — файл src/app/worker/market.worker.ts. На start он останавливает прежний таймер пачек, вызывает free() у старого MarketGenerator и сбрасывает кадр снимка. Потом загружает Wasm, если модуль ещё не загружен. Если за время загрузки пришёл более новый start, старое продолжение генератор не создаёт: оно сравнивает runId. Иначе Worker создаёт новый MarketGenerator и новую InstrumentBook, отвечает started и запускает BatchPump.

BatchPump после каждой пачки ставит один setTimeout на интервал сессии. Это не setInterval. Пауза снимает таймер. Resume ставит один следующий тик и не создаёт пачки за время простоя.

На тике Wasm-функция fillBatch пишет в линейную память ровно столько событий, сколько просили. Одно событие — семь чисел i32: индекс инструмента, цена сделки в центах, tradeQuantity, bid, ask и два количества стакана. Цена внутри — целое число центов: 10200 значит $102.00. Цена следующей сделки получается из предыдущей цены этого инструмента, шаг не больше 15 центов, цена больше нуля, bid строго меньше ask, цена сделки равна bid или ask этого же события.

Адаптер readMarketUpdates читает эти семь чисел и копирует их в объекты MarketUpdate. Метрики он не считает. Индекс он превращает в имя из того же списка, который фабрика передала генератору. Сразу после чтения числа уже обычные поля JavaScript: следующая запись в Wasm-память их не затрёт.

Дальше InstrumentBook находит аккумулятор этого имени и отдаёт событие пяти Стратегиям. У каждого инструмента свой аккумулятор. ALFA и BETA не складывают суммы в один объект. Общий цикл только вызывает update. Формула живёт в стратегии. История событий не хранится: после update объект MarketUpdate можно забыть.

SnapshotGate помечает снимок таблицы грязным сразу, а в главный поток отправляет его не чаще одного animation frame. К этому моменту каждая сделка пачки уже учтена в суммах. Что именно лежит в снимке и чем он не является, разобрано ниже. Сообщение называется snapshot и несёт runId вместе со строками инструментов.

На главном потоке Заместитель RunGuard сравнивает runId с текущей сессией. Если номер чужой, сообщение выбрасывается целиком: фасад не читает ни строки, ни текст ошибки. Если номер свой, фасад кладёт строки в snapshot$, а статусы started и failed переводит в фазу running или failed.

snapshot$ и status$ — это RxJS Observable. Так в проекте сделан Наблюдатель. Страница не хранит свой список слушателей. В шаблоне подписка — pipe async. Когда компонент уничтожается, подписка снимается. Dashboard рисует таблицу. Settings рисует форму. Оба видят один и тот же фасад.

Связь короткая. Страница вызывает фасад. Фасад выполняет команду. Команда двигает состояние и, если это Apply, просит фабрику создать сессию. Фасад отправляет сообщение в Worker. Worker просит Wasm сделать пачку, адаптер превращает память в MarketUpdate, стратегии обновляют суммы, кадр отправляет снимок. RunGuard пускает снимок только с текущим runId. Observable доносит его до шаблона.

Один взгляд на все связи

Блок-схема системы

Светлые блоки живут в главном потоке страницы. Тёмная колонка — один Web Worker. Стрелка вниз — прямой вызов или следующее сообщение. Обратно из Worker в страницу поднимается уже не пачка MarketUpdate, а снимок таблицы.

Что такое снимок

В проекте слово «снимок» встречается в двух разных местах, и это не одно и то же.

Снимок стакана сидит внутри одного MarketUpdate. Это четыре числа последнего события: bidCents, askCents, bidQuantity, askQuantity. Из него стратегии Last не берут ничего, а Spread и Imbalance берут только его. Следующее событие того же инструмента затирает предыдущий листок стакана. Сумма за день из этих чисел не строится.

Снимок таблицы — это сообщение snapshot, которое Worker отправляет в главный поток. Его тип в коде — список InstrumentSnapshot. Это не пачка сделок и не архив. Это ответ на вопрос «что написать в каждой строке прямо сейчас», если сложить всё, что уже случилось с начала этого runId, и взять последний стакан.

В одной строке снимка таблицы шесть полей.

Поле Откуда взялось
symbol Имя из списка сессии, в том же порядке: ALFA, потом BETA.
last Цена последней сделки в центах либо «недоступно».
spread Разница последнего ask и bid в центах либо «недоступно».
volume Сумма tradeQuantity за весь текущий запуск. До сделок это 0.
vwap Две суммы, числитель и знаменатель, а не уже округлённые доллары. Знаменатель 0 — «недоступно».
imbalance Доля от −1 до +1 по последнему стакану либо «недоступно».

Рядом со строками сообщение всегда несёт runId. Без него RunGuard не смог бы отличить сводку новой смены от письма, которое ещё ехало от старой. Фасад не прибавляет новый снимок к предыдущему. Он заменяет весь список строк. Поэтому два одинаковых сообщения подряд не удваивают Volume: на экране просто ещё раз те же итоги.

Снимок появляется в двух моментах. В момент Apply фасад сам публикует пустой снимок, blankSnapshot: цены и дисбаланс недоступны, объём 0, имена уже новые. Это происходит на главном потоке сразу, не дожидаясь первой пачки. Потом Worker, уже после того как стратегии учли сделки, отдаёт наполненный снимок. Пока Wasm ещё стартует, на экране виден именно пустой.

Пачка может содержать 1000 событий, а кадров в секунду около шестидесяти. SnapshotGate не шлёт снимок после каждого события. Он помечает данные грязными сразу, а postMessage делает один раз за кадр. Если за кадр прошли две пачки, в ушедшем снимке уже обе: сделки не ждут отправки, они пишутся в суммы до отправки. На стене при этом не появляется лента из двух тысяч MarketUpdate.

После паузы новый снимок сам по себе не рождается, потому что новые пачки не запрашиваются. Уже поставленный в очередь кадр может один раз донести сделки, которые были учтены до Pause. Это не новая генерация. История этих сделок всё равно не сохраняется: в памяти остаётся только последний снимок и текущие суммы.

Так выглядит наполненный снимок одной строки после примера из задания.

snapshot
  runId: 2
  rows:
    symbol: ALFA
    last:       price, 10200 центов
    spread:     price, 4 цента
    volume:     quantity, 40
    vwap:       notional 406000, volume 40
    imbalance:  ratio, 0.20

Доллары $102.00, $0.04 и $101.50 в этот объект не входят. Их считает formatMetric уже в Dashboard, когда шаблон читает snapshot$. Округление происходит там, а не в стратегиях и не в Wasm.

Пять метрик

До первых данных Last, Spread, VWAP и Imbalance недоступны. На экране это текст «н/д». Volume равен 0, и это нормальное число, не «неизвестно». Если в формуле знаменатель 0, стратегия тоже возвращает «недоступно», а не NaN.

Метрика Что хранит стратегия Формула
Last последний priceCents цена последней сделки
Spread последние bid и ask askCents − bidCents. Старые снимки стакана не суммируются.
Volume сумма tradeQuantity с начала запуска количества стакана в объём не входят
VWAP две суммы за всю смену, без окна по времени sum(priceCents × tradeQuantity) / sum(tradeQuantity)
Imbalance последние количества стакана (bidQuantity − askQuantity) / (bidQuantity + askQuantity), от −1 до +1

Суммы Volume и VWAP хранятся как bigint. Обычный number после 2^53 перестаёт точно помнить младшие единицы. Деление и округление до центов на экране делает только formatMetric. Пример из задания считается так.

Две сделки: 10 штук по $100 и 30 штук по $102.

Last = $102.00. Volume = 40.

VWAP = (100×10 + 102×30) / 40 = $101.50.

Последний стакан: bid $101.96, ask $102, поэтому Spread = $0.04.

Bid quantity 600, ask quantity 400, поэтому значение Imbalance = 0.20. На экране formatMetric показывает +0.20: плюс у положительной доли, ноль без знака. Volume на экране пишется с разделителями тысяч.

Этот пример проверяет src/app/metrics/metrics.spec.ts. Тест идёт через InstrumentBook, тем же циклом, что и Worker.

Три действия пользователя

Pause, Resume и Apply

Пока Wasm ещё поднимается, фаза starting, на Dashboard написано «Запуск генератора…», в таблице пустые строки. Если модуль не загрузился, Worker присылает failed с русским текстом. Фасад переходит в failed, и на странице виден role="alert", а не пустой экран.

Pause из running переводит фазу в paused и посылает Worker сообщение pause с текущим runId. Worker снимает таймер. Суммы и таблица не обнуляются. Сообщение pause со старым runId новый запуск не останавливает: Worker сравнивает номер с текущей сессией.

Resume возвращает фазу в running и ставит один будущий тик. Сделки за время паузы не создаются. Повторный Pause в паузе и повторный Resume на ходу команду не выполняют.

Форма Settings до кнопки Apply фасад не вызывает. Поля проверяет Цепочка обязанностей. У каждого поля два звена: IntegerLink, затем RangeLink. Третьего звена нет. Если значение не целое, диапазон этого поля уже не смотрит. Остальные поля проверяются всё равно, и форма показывает весь список ошибок. parseDraftNumber пропускает дальше только десятичные цифры, поэтому «5.5», «0x10» и «1e3» остаются строками и не превращаются молча в число. Пустое поле получает текст «Поле обязательно.». После успешного Apply поля показывают уже применённые значения. ApplySettingsCommand вызывает parseSettings один раз.

Поле По умолчанию Диапазон
instrument count51–50
updates per batch1001–1000
batch interval ms50050–2000

100 событий за 500 мс — это 200 событий в секунду на все инструменты вместе. Один инструмент может встретиться в пачке несколько раз. Потолок задания — 1000 событий каждые 50 мс, то есть 20 000 событий в секунду. В главный поток при этом уходит не лента событий, а один снимок на кадр.

Если числа верные, Apply из любой фазы, включая паузу и ошибку, создаёт новый runId, чистые суммы и снова запускает генерацию. Это не Resume. Старые итоги не продолжаются. Письмо со старым runId, которое придёт позже, не меняет ни одну цифру нового снимка.

Раздел паттернов

Как паттерн работает вообще и где он в проекте

Каталог, из которого взяты имена: refactoring.guru/ru/design-patterns. Ниже у каждого паттерна сначала общий механизм, потом место в этом коде. Имена паттернов в тексте ведут сюда.

Одиночка

Одиночка гарантирует один экземпляр объекта на всю программу и одну точку доступа к нему. Иначе каждый новый кусок интерфейса создал бы свою копию и состояние разъехалось бы.

Одиночка на refactoring.guru

Здесь один ProducerFacade и через него один WorkerClient. Экземпляр даёт Angular DI: @Injectable({ providedIn: 'root' }). Класса с getInstance() нет. Фасад создаётся в app.config.ts при старте приложения. Страницы его только внедряют. Поэтому маршрут не создаёт второй Worker. При уничтожении фасада Worker завершается один раз.

Состояние

Состояние хранит режим объекта и таблицу разрешённых переходов. Действие либо переводит объект в новую фазу, либо отклоняется. Поведение не размазано по отдельным флагам «мы на паузе» и «мы сломались», которые можно включить одновременно.

Состояние на refactoring.guru

SessionMachine в session-machine.ts знает фазы idle, starting, running, paused, failed. Pause ведёт из running в paused. Resume возвращает в running. Apply из любой фазы ведёт в starting, а ответ Worker started переводит в running. Ошибка старта и ошибка уже идущей генерации обе ведут в failed. На дашборде это «Ошибка инициализации» и «Ошибка генерации». Запрещённый переход не меняет фазу и не доходит до Worker. Сам таймер пачек после разрешённой паузы живёт в BatchPump: он не копит пропущенные тики.

Фабричный метод

Фабричный метод прячет создание объекта в одном методе. Клиенты получают готовый продукт и не собирают его поля сами. Так нельзя случайно создать объект в обход правил.

Фабричный метод на refactoring.guru

Продукт здесь — сессия. Метод SessionFactory.create выдаёт новый runId, имена инструментов, seed и параметры пачки. Вызывает его только ApplySettingsCommand, и только после успешной валидации и разрешённого перехода apply. Dashboard и Settings фабрику не знают. Чистые суммы и объект MarketGenerator появляются уже в Worker из этой сессии, потому что и Wasm, и аккумуляторы должны жить там. Старый генератор до этого освобождается через free().

Фасад

Фасад даёт простой интерфейс к подсистеме. Клиент вызывает несколько понятных методов и не обходит внутренние объекты сам.

Фасад на refactoring.guru

ProducerFacade отдаёт страницам snapshot$, status$, appliedSettings$, pause(), resume(), apply() и текущие настройки. Компонент не видит Worker, Wasm, runId и линейную память. Внутри фасад держит состояние, фабрику, команды, RunGuard и WorkerClient.

Команда

Команда упаковывает действие в объект с методом выполнения. Инициатор действия и исполнитель пользуются одним объектом. Появляется один путь, а не копия логики в кнопке и отдельно в тесте.

Команда на refactoring.guru

В commands.ts три класса: PauseCommand, ResumeCommand, ApplySettingsCommand. Фасад только создаёт команду и вызывает execute. Четвёртой команды нет. Apply возвращает список ошибок валидации. Pause и Resume возвращают, разрешил ли переход. Общий интерфейс «на будущее» с одним типом результата не вводился.

Заместитель

Заместитель стоит перед объектом и решает, пропускать обращение или нет. Защищающий заместитель отсекает недопустимые запросы до того, как настоящий получатель их увидит.

Заместитель на refactoring.guru

RunGuard.accept получает сообщение Worker. Если runId не равен текущей сессии, метод возвращает null. Фасад на этом выходит и не применяет ни снимок, ни текст ошибки. Так результат прошлого запуска не затирает новый. В Worker та же проверка стоит на запоздавшем start, pause и resume.

Адаптер

Адаптер переводит чужой интерфейс в интерфейс, который ждёт остальная программа. Клиенты не учат формат внешней системы.

Адаптер на refactoring.guru

Внешняя система здесь — линейная память Wasm. readMarketUpdates читает семь i32 на событие и возвращает список MarketUpdate. Доменный тип описан в market-update.ts. Стратегии и компоненты не знают про WebAssembly.Memory и указатель. Адаптер метрики не считает. Порядок полей совпадает с fill_batch в wasm/market-producer/src/lib.rs.

Стратегия

Стратегия выносит вариант алгоритма в отдельный объект с общим интерфейсом. Клиент передаёт данные каждой стратегии одинаково и не содержит сами формулы.

Стратегия на refactoring.guru

Интерфейс — update(event) и read(). Пять классов: LastPriceStrategy, SpreadStrategy, VolumeStrategy, VwapStrategy, ImbalanceStrategy. InstrumentAccumulator в цикле только вызывает их. InstrumentBook держит отдельный аккумулятор на имя. Last и Spread с Imbalance смотрят последний снимок. Volume и VWAP копят суммы. Недоступное значение — явный результат стратегии.

Наблюдатель

Наблюдатель позволяет объектам подписываться на изменения другого объекта. Источник не знает конкретных подписчиков. Он публикует значение, а подписчики сами решают, как его показать.

Наблюдатель на refactoring.guru

В этом проекте наблюдатель — RxJS. Фасад держит BehaviorSubject и отдаёт наружу snapshot$, status$ и appliedSettings$. Страница подписывается через async. Своего списка колбэков нет. BehaviorSubject хранит последнее значение, поэтому новая страница сразу видит текущую сессию, а не ждёт следующей пачки.

Цепочка обязанностей

Цепочка передаёт запрос по звеньям. Звено либо обрабатывает его и останавливает цепочку, либо отдаёт следующему. Порядок проверок виден в сборке цепочки, а не спрятан в одном длинном условии.

Цепочка обязанностей на refactoring.guru

Звенья — IntegerLink и RangeLink. Метод integerThenRange соединяет их через setNext. На каждое поле собирается своя цепочка с его min и max. Первая ошибка звена заканчивает эту цепочку. Три поля проверяются все. Apply с непустым списком ошибок сессию не меняет. Границы: число инструментов 1–50, событий в пачке 1–1000, интервал 50–2000 мс.

Двенадцать паттернов, которые не использованы

Они есть в каталоге refactoring.guru. В этом проекте у них нет работы.

Паттерн Почему его нет
Строитель Настройки — три числа. Их задаёт объект, а не пошаговая сборка.
Прототип Клон живой сессии унёс бы старые суммы. Сессию каждый раз создаёт фабрика.
Абстрактная фабрика Семейств продуктов нет. Сессия одна, генератор один, снимок один.
Мост Нет двух иерархий, которые надо менять независимо. Граница Wasm — это адаптер.
Компоновщик Инструменты — плоский список строк, не дерево частей.
Декоратор Формат валюты — функция formatMetric, не обёртка над стратегией.
Приспособленец Суммы инструмента нельзя делить между именами. Иначе ALFA и BETA смешают объём.
Итератор Пачка — массив. Её обходит обычный цикл.
Посредник Он повторил бы фасад. Dashboard и Settings друг с другом не согласуют действия.
Хранитель Задание запрещает хранить историю. Пауза не откатывает прошлый снимок, она перестаёт запрашивать пачки.
Шаблонный метод Общий алгоритм — один цикл update. Базовый класс с шагами ничего не спрячет.
Посетитель Нет дерева объектов для двойной диспетчеризации. Формула живёт в стратегии.

Запуск: npm install, затем npm start. Тесты: npm test и npm run test:generator.
